## Implementation and interfaces

- Historical checker copied byte-for-byte into src/legacy/check_conformance_v1.py.
- load validates required CSV fields, decimal quantities, timestamps, duplicate
  event IDs/exact anonymous duplicates, item/unit consistency, and unsupported
  returns/reversals. check_case also validates its direct-call inputs.
- check_case retains its seven-item tuple. Rule values are True/False/None;
  quantity outputs are Decimal-or-None event totals, missing performance is None.
- Every ordering target is checked. R4 uses the next PO per modification.
  Timestamps tied at a required boundary do not establish compliance.
- R3 uses cumulative invoice and receipt event deltas at each invoice timestamp.
  Same-time receipts cannot invent ordering; provable violations dominate unknowns.
- write_results(cases, output_dir, tag) returns exactly
  {'conformance': Path, 'summary': Path}.
- Conformance columns: case_id,scenario,variant_short,violations,cycle_days,
  qty_received,qty_invoiced,not_evaluable,status,rule_version.
- Summary retains historical aggregate fields and adds compliant,violating,
  not_evaluable,evaluated_cases,rule_version and per-rule *_not_evaluable counts.
  Conformance rate uses compliant/(compliant+violating), blank when unevaluated.
  A proven violation takes case status precedence; unknown rules remain listed.
- Run manager --output-dir is a data root: runs/<tag>/ holds directly written
  logs/results; runs.csv is at that root. Exclusive mkdir prevents collisions.
  Safe tags, n>0, and unique default IDs prevent clobber/traversal.
- Run registry columns: run_id,utc_time,era,n_per_scenario,seed,cases,events,
  viol_rate,mean_cycle,compliant,violating,not_evaluable,evaluated_cases,rule_version.
  Rates use evaluated cases. compute_metrics returns a dictionary with the
  numeric metrics/status counts; no other current caller used its old tuple.
- Noise output keeps noise_level,seed,recall,fpr and adds target_evaluated,
  target_not_evaluable,s1_evaluated,s1_not_evaluable,rule_version. No pandas or
  fallback rule copy; its stdlib seeded samples are explicitly versioned v2.
- docs/event-contract.md documents required schema, rules, examples/commands,
  result paths, denominator interpretation, and limits.

## Self-review and bounded limitations

Reviewed realistic mutations: first-event-only processing, reuse of receipt
quantity per invoice, future receipt repair, zero-coercion of blanks, tie sorting,
unsafe paths, duplicate run reuse, unknown-as-compliant classification, and
central output writes each have an observable fixture assertion.

No universal policy/causal savings claim is made. Activity names are explicit;
returns/reversals need a separately designed contract. Partially failed runs
retain their reserved directory and are not silently retried. Existing legacy
runs.csv headers are rejected for v2 writes; use a fresh output root. The v1
snapshot remains unchanged, including its historical script-relative defaults;
reproducibility tests call its load/check_case API with explicit input paths.
No ERP execution, deployment, or publication is claimed.
