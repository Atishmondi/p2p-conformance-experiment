**Status: readiness complete; ERP execution unverified.** The checked-in [`erp-recorded-events.csv`](../examples/erp-recorded-events.csv) is a **synthetic contract fixture**. It is not an Odoo export or evidence of any configured control. The SQL entry point fails closed. ## Source proof before running the checker

Use a disposable Odoo 17 database and distinct requester, approver, buyer, warehouse, and accountant actors. Freeze the installed image digest, modules, settings, actors, product/UoM mapping, detector commit and test arm in a run record. Observe and record actual actions at the point of occurrence: request submission, approval/re-approval, PO confirmation, each completed receipt movement, each posted vendor bill line, and payment registration. `PO Modification` needs a captured post-approval edit with prior/new values and actor. Approval workflow changes alone must not be labeled modifications. The standard document's latest `write_date`/`write_uid`, `date_order`, planned receipt date, vendor bill date, and current `qty_received`/`qty_invoiced` cannot reconstruct prior actions. If the installed Odoo configuration does not provide immutable history for an action, instrument the action before the pilot and validate the hook and persisted audit table with known attempts. Keep audit record ID, actor, precise timezone-aware recorded timestamp, original document ID, line ID, action and old/new values. Reconcile source IDs to the actual audit records in the demo database or exported audit trail; independently spot-check the row, actor, action and timestamp. A syntactically valid `source_id` or `timestamp_kind=recorded` does **not** attest authentic ERP history.

Map exactly one comparable product and UoM to each `case_id`. Split a multi-line PO into separate case IDs using an explicit stable mapping; retain the parent PO ID as metadata. `source_model` and `source_id` identify the captured **action record**, unique per emitted event; `event_id` is unique throughout export. `source_action` names that action. Receive and invoice rows carry **event deltas** at this same item/UoM grain; do not repeat current line totals across events. For partial receipts or bills, use each validated movement or posted bill line once. Reversals, returns, credits, cancelled actions and quantity adjustments require a new contract and must not be silently represented as positive deltas. Only allow the eight activity names accepted by the adapter. The exact invoice event linked to each payment is `invoice_event_id`, looked up within the same case; for allocations across several invoices, produce separately attributable links only when actual source evidence supports them, or stop. No memo/name inference. R5 checks recorded temporal precedence, **not full financial settlement or amount reconciliation**.

`source_action` is a closed **adapter code**, not an assertion about Odoo's native event names. Before export, map each real instrumented action and its source record to exactly one code below; inspect its state transition/direction and reject any credit, return, reversal, refund or cancellation source action rather than re-labeling it. A mapped code is still subject to independent source proof.

| `activity` | Required `source_action` | Action to verify against audit trail |
| --- | --- | --- |
| `Purchase Request` | `request_submitted` | Request submission |
| `Purchase Request Approval` | `request_approved` | Approval action |
| `Purchase Request Approval (re-approval)` | `request_reapproved` | Subsequent approval action |
| `PO Modification` | `po_modified` | Post-approval commercial edit, with before/after values |
| `Purchase Order` | `po_confirmed` | Order confirmation |
| `Goods Receipt` | `receipt_validated` | Completed positive receipt movement |
| `Vendor Invoice` | `vendor_bill_posted` | Posted positive vendor bill line, not credit note/reversal |
| `Payment` | `payment_registered` | Registered vendor payment linked to bill event |

The adapter rejects every unknown or mismatched code, including a reversal described in `source_action` on a `Vendor Invoice` row. The exporter/operator must verify source direction because substituting a permitted code for a reversal is misrepresentation the CSV cannot detect.

The CSV requires `case_id,activity,timestamp,event_id,source_model,source_id,source_action,timestamp_kind,product_id,uom`. Only `timestamp_kind=recorded` and timezone-aware ISO datetimes qualify. Optional fields are `invoice_event_id,qty_ordered,qty_received,qty_invoiced,scenario,resource,vendor,po_id`. Payment requires `invoice_event_id`; Goods Receipt requires `qty_received`; Vendor Invoice requires `qty_invoiced`. `qty_ordered` belongs only to Purchase Order. Do not put vendor dates or manual `timestamp_occurred` into the verdict input; record those in a separate mechanism/attempt log with distinct provenance. Quantities are finite nonnegative decimals. The adapter trims case and event IDs and invoice links, rejects duplicates, mixed product/UoM grain, unknown actions, missing source links, unsupported quantities and unmapped payments, then normalizes UTC and writes deterministic checker-compatible CSV. The linked invoice may be later than its payment: this well-formed adverse ordering reaches R5 as a violation; an equal recorded timestamp remains unknown. It validates shape and relationships, **not authenticity**.

## Bounded trial and outcome log

Preregister each scenario and its expected control behavior before execution. Run a small S1 normal flow, S3 bill-before-receipt attempt and receipt-control attempt, S4 excess bill attempt and quantity-control attempt, S6 post-approval edit/confirmation attempt and reapproval-control attempt. Capture each attempted action and actual UI/API result (accepted, warning, blocked), actor, wall time, screenshot or immutable audit reference, configuration before/after, and actual recorded events. Blocked attempts are **attempt records**, not invented recorded invoice/PO events. Include approval-only change as an R4 negative control. Do not assume Odoo's bill control or two-step approval necessarily blocks posting; verify the installed behavior. The official Odoo 17 bill-control documentation describes received-quantity matching and a “Should Be Paid” status, but that alone does not establish a hard posting/payment block or a complete audit history: <https://www.odoo.com/documentation/17.0/applications/inventory_and_mrp/purchase/manage_deals/control_bills.html>.

For each case, retain source action references, item/UoM, scenario, attempt outcome, occurred vendor/physical dates separately, recorded timestamps, invoice links, checker version, per-rule True/False/None and reason for each None. R1 approval before PO, R2 receipt before each invoice, R3 cumulative billed vs receipts available at each invoice, R4 reapproval between edit and next PO, and R5 the **linked** invoice before each payment are the v2 temporal/quantity tests. For S3, compare occurred-early and recorded-early separately; missing recorded source action means unknown, not compliant. Report each arm's violation, evaluated and unknown denominators; do not claim savings, hard enforcement, or field transfer from fixture runs. Stop and audit source provenance on any missing or conflicting action trail. Keep the preregistration, settings, images, instrumentation code/hash, export hash, source spot checks and attempted-action log before claiming a real result.
